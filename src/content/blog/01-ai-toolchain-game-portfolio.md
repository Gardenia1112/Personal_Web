把作品集当成一个「可交互的工位」，而不是一堆截图墙，是这次站点最核心的产品决策。需求拆解时，我把页面分成三层：深夜工位首页负责第一印象，桌面文件夹承载项目与美术入口，博客则用来沉淀可复用的技术笔记。

AI 在流程里主要做三件事：补全样板代码、把设计文档翻译成可跑的组件骨架、以及在重构时对照「不改 Nav / 不改奖项入口」这类硬约束做 diff 自检。真正决定质量的，仍然是人定的边界——例如 Content Collections 只放博客、业务文案继续走 `src/data/`，避免两套真相源互相打架。

落地时我习惯把「可验证」写进每一步：本地 `astro build` 必须出齐路由，静态资源路径必须对得上 `public/`，交互脚本则用幂等初始化防止转场后重复绑定。下面是一段示意：用集合过滤草稿，再按日期倒序，保证列表页永远只露出可发布内容。

```ts
const posts = (await getCollection("blog", ({ data }) => !data.draft)).sort(
  (a, b) => b.data.date.valueOf() - a.data.date.valueOf(),
);
```

工具链不会替你做品味判断，但它能把重复劳动压到最低。接下来几篇会分别写性能优化与状态机架构，把客户端侧更硬核的部分拆开讲。
